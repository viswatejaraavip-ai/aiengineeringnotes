Threads in the RAG preprocessing pipeline

A RAG ingestion pipeline is a chain of stages with three different bottlenecks: waiting on the network, burning CPU, and feeding a GPU. Threads are the right tool for exactly one of those. Here is how to tell which stage is which, what to use for each, and how to join them so that a fast stage cannot drown a slow one.

21 Oct 202611 min read
The short version

Threads for stages that wait: fetching, calling embedding and model APIs, upserting to the vector store. Processes for stages that compute: parsing, OCR, tokenising. One batching consumer for a local GPU. Join the stages with bounded queues so backpressure flows upstream, cap in-flight requests below the rate limit, and make every write idempotent so a retry is free.

01The six stages and what each waits on

Strip any ingestion pipeline down and it is the same six steps. What differs is what each step is waiting for.

StageWhat it doesBottleneckTypical wait
FetchDownload the document from a drive, a bucket, a wiki, a crawlNetwork I/O50 ms to seconds
ParsePDF to text, HTML to tree, OCR, table extractionCPU, sometimes memory10 ms to tens of seconds
ChunkSplit on structure, count tokens, build parent and child recordsCPU, lightMilliseconds
EnrichModel-generated metadata, summaries, contextual prefixesNetwork I/O to an API, with a rate limit0.5 to 5 seconds
EmbedText to vector, by API or on a local GPUNetwork I/O, or GPU throughput100 ms to 1 second per batch
UpsertWrite vectors and metadata to the storeNetwork I/O, with a batch size50 to 500 ms per batch

Four of the six are waiting on something over the network. One is pure computation. One is either, depending on where the embedding model runs. That split decides everything that follows.

02Why the serial version is slow

The first version of every pipeline is a for loop. For a corpus of 100,000 chunks with one API-bound stage at 200 milliseconds per call, the arithmetic is unforgiving.

ApproachCallsIn flightWall time
Serial, one chunk per call100,00015.6 hours
Threaded, one chunk per call100,0003210 minutes
Threaded, 64 chunks per call1,5638about 1 minute

The serial loop is slow not because the machine is busy but because it is idle. Almost all of those 5.6 hours are spent waiting for a reply with the CPU at one or two percent. That is the signature of an I/O-bound stage, and it is the case where threads pay off most.

03What a thread buys you in Python

Most ingestion code is Python, and Python's global interpreter lock means only one thread runs Python bytecode at a time. This is the fact that trips people up, so it is worth being precise about what it does and does not cost.

  • While a thread waits on a socket, the lock is released. Thirty-two threads each waiting on an HTTP reply are thirty-two requests genuinely in flight. The lock does not serialise waiting. For I/O-bound stages, threads give near-linear speedup until the remote side pushes back.
  • While a thread runs pure-Python computation, it holds the lock. Thirty-two threads parsing documents in a pure-Python parser take turns, and the total is no faster than one thread, often slower from the switching. For CPU-bound stages, threads are the wrong tool.
  • C extensions may or may not release the lock. NumPy, many PDF libraries and tokenisers written in Rust or C release it during heavy work, so threads can help with those. The only way to know is to measure one thread against four on the real stage.
  • Processes sidestep the lock. A process pool runs one interpreter per worker, so CPU-bound stages scale with cores. The cost is that inputs and outputs are pickled across the boundary, which matters for large documents and is why the parse stage should receive a path and return text, not receive bytes and return a parsed object graph.
  • asyncio is the other way to wait. One thread, many coroutines, each suspended on its own socket. It handles thousands of concurrent requests with less memory than threads, and most provider SDKs ship an async client. It is the better choice for the API-bound stages when the surrounding code is already async; threads are fine when it is not.

04Picking the model per stage

StageUseConcurrency to start with
FetchThread pool or asyncio16 to 64, bounded by the source's rate limit
ParseProcess poolNumber of cores, minus one
ChunkInline in the parse workerNone needed
EnrichThread pool or asyncio, with a semaphoreJust under the provider's requests-per-minute limit, divided by the per-call latency
Embed, by APIThread pool or asyncio, batched8 to 16 batches in flight
Embed, local GPUOne consumer thread with a batcherOne. The GPU is the parallelism.
UpsertThread pool, batched4 to 8 batches in flight

The local GPU row deserves a sentence. A GPU does its parallel work inside a single call on a batch of inputs. Several threads each sending small batches fight for the device and lose the benefit of the batch. One consumer that drains the queue into batches of 64 or 128 and calls the model once per batch will beat eight threads calling it with one chunk each, every time.

In code, an I/O-bound stage with a cap on in-flight requests looks like this:

from concurrent.futures import ThreadPoolExecutor, as_completed

def embed_batch(batch):            # one HTTP call, returns list of vectors
    ...

with ThreadPoolExecutor(max_workers=12) as pool:
    futures = {pool.submit(embed_batch, b): b for b in batches}
    for fut in as_completed(futures):
        batch = futures[fut]
        try:
            vectors = fut.result()
        except RateLimited:
            requeue(batch)         # see the retry section
        else:
            upsert_queue.put((batch, vectors))

And the CPU-bound stage next to it hands paths, not bytes, to a process pool:

from concurrent.futures import ProcessPoolExecutor

def parse_and_chunk(path):         # returns a list of small chunk dicts
    text = parse(path)
    return chunk(text, doc_id=path.stem)

with ProcessPoolExecutor(max_workers=os.cpu_count() - 1) as pool:
    for chunks in pool.map(parse_and_chunk, paths, chunksize=4):
        for c in chunks:
            enrich_queue.put(c)    # blocks when the queue is full

05Joining stages: bounded queues and backpressure

Once each stage has its own concurrency, the question is how they hand work to each other. The answer is a queue between every pair of stages, and the queue must have a maximum size.

The bound is what makes the pipeline safe. Parsing is fast and enrichment is rate-limited, so without a bound the enrich queue grows until the process runs out of memory, usually an hour in, usually at night. With a bound of a few hundred items, the parse stage blocks when enrichment falls behind, which blocks fetch, and the whole pipeline settles at the speed of its slowest stage with bounded memory. That is backpressure, and it costs one argument to the queue constructor.

Size the queues at a few times the downstream stage's batch size, enough to keep it fed through jitter and no more. A queue that is always full is telling you where the bottleneck is. A queue that is always empty is telling you the stage before it is the bottleneck. Log the queue depths; they are the best profiler the pipeline has.

06Rate limits, retries and the in-flight cap

The API-bound stages do not scale with threads forever. They scale until the provider's rate limit, and then every extra thread adds a 429 response, a retry, and a wait. Beyond the limit, more concurrency makes the stage slower.

  • Cap in-flight requests with a semaphore, separate from the thread count. Set it from the provider's published limits: requests per minute divided by sixty, times the typical latency in seconds, gives the number of requests that can be in flight without exceeding the rate. Leave headroom for the production traffic that shares the same key.
  • Retry with exponential backoff and jitter, honouring the retry-after header when one is given. Jitter matters: without it, thirty-two threads that got a 429 together retry together and get another one together.
  • Treat the retry budget as a stage metric. If more than a few percent of calls are retried, the cap is too high. Lower it; throughput goes up.
  • Separate the queue for failures. A chunk that failed three times goes to a dead-letter list with the error, and the pipeline moves on. One malformed PDF or one chunk that trips a content filter must not stall the other 99,999.

07Batching: the other concurrency

Threads overlap waiting. Batching removes it. Embedding APIs accept dozens to hundreds of texts per call, vector stores accept hundreds of records per upsert, and a local model wants its inputs in batches anyway. Sixty-four chunks per embedding call is sixty-four times fewer round trips, and the per-call latency barely grows. Batch first, thread second: the threaded single-chunk row in the table above is ten minutes, the batched one is a minute.

For the model-generated enrichment stage there is a third option that removes the concurrency problem entirely. Provider batch APIs take a file of requests, run them over hours at a reduced price, and return a file of results. No threads, no rate limits, no retry logic, at the cost of latency you do not care about during a bulk ingest. For a first full load or a re-index after a prompt change, this is usually the right answer, and the threaded path is for the incremental trickle afterwards.

08Idempotency, ordering and checkpoints

Concurrency means things finish out of order and some things finish twice. The pipeline has to be built so neither matters.

  • Deterministic ids. A chunk's id is a hash of its document id, section and position, or of its content. Upserting the same chunk twice overwrites one record rather than creating two. Every retry and every re-run becomes safe.
  • No dependence on order. Chunks of one document arrive at the upsert stage interleaved with chunks of others. Parent records should be written before, or independently of, children, and nothing downstream should assume that chunk 7 arrives after chunk 6.
  • Checkpoint at the document level. Record a document as done only after all of its chunks are upserted. On restart, skip done documents and re-run the rest from the start. Re-running a partially ingested document is free because of the deterministic ids; tracking individual chunks is not worth the bookkeeping.
  • Version the pipeline in the metadata. Prompt version, chunker version, embedding model. A later selective re-index can then target exactly the records that an old version produced.

09Pitfalls that look like bugs elsewhere

  • Clients that are not thread-safe. Some SDKs and database drivers must not be shared across threads. Create one per worker, or use a pool. The symptom is intermittent corrupt responses that never reproduce in a single-threaded test.
  • Connection pool exhaustion. Thirty-two threads and a default HTTP pool of ten connections means twenty-two threads waiting on the pool, not on the network. Set the pool size to match the thread count.
  • A tokeniser or model loaded per task. Loading a tokeniser inside the worker function means loading it a hundred thousand times. Load once per process, at worker start, and reuse.
  • Pickling large objects to a process pool. Sending a 50 MB PDF's bytes to a worker, and getting a large object back, can cost more than the parse. Send paths, return small chunk records.
  • Forking after threads exist. Starting a process pool from a process that already has threads running, or has initialised a CUDA context, deadlocks or crashes on some platforms. Use the spawn start method, or create the process pool first.
  • Logging from many threads to one file. Interleaved lines and lost messages. Use the logging module's queue handler, or log structured events with the chunk id so they can be reassembled.
  • Silent partial success. A pool that swallows exceptions in futures nobody checks. Always consume every future's result, and count failures as a first-class metric.

10What the Purana ingest did

The Purana pipeline is a small, concrete example of choosing per stage. Parsing seventeen GRETIL text files with five different verse-reference conventions is pure CPU, and at seventeen files it needs no pool at all; the effort went into the parser's correctness, not its speed. The model-generated chapter cards, 2,389 of them, went through the batch API as six batches submitted in one afternoon, every one back within about an hour, with no thread pool, no rate-limit handling and no retry code at all. The validation step then checked every returned card, repaired twelve by mapping and regenerated the handful that failed, which is the dead-letter pattern in miniature. The lesson is not that threads were avoided; it is that for a one-time bulk load, the batch API removed the stage that would have needed them.

11Takeaways

  1. Classify each stage by what it waits on. Network, CPU or GPU. The classification picks the tool.
  2. Threads or asyncio for waiting, processes for computing, one batcher for a GPU. Python's interpreter lock makes this a rule, not a preference.
  3. Batch before you thread. Fewer round trips beats more overlapped ones.
  4. Bounded queues between stages. Backpressure is one constructor argument and it is what keeps memory flat overnight.
  5. Cap in-flight requests under the rate limit, retry with jitter, dead-letter the rest. Above the limit, more threads make it slower.
  6. Deterministic ids and document-level checkpoints. Then retries, re-runs and restarts are all free.
  7. For the bulk load, consider no threads at all. A provider batch API turns the hardest stage into a file upload.
