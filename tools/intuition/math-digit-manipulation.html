Start with what you would do by hand

Reverse the number 123 to get 321. On paper you would write the digits down and read them backwards. A computer does not hold a number as digits; it holds a single value, so "read the digits backwards" has to be built from arithmetic. The two operations that expose digits are remainder and integer division: 123 mod 10 is 3, the last digit, and 123 divided by 10 with the fraction thrown away is 12, the number with that digit removed.

The by-hand alternative is converting to a string, reversing it, and converting back. That works, but it allocates memory, it hides what is happening, and interviewers want to see that you can handle overflow and signs, which strings do not help with.

Build the structure, one piece at a time

There are two variables. x is the number still to be read, and rev is the number built so far. Each step peels the last digit off x and pushes it onto the right end of rev; pushing a digit onto the right end means multiplying by 10 and adding:

stepxdigit = x mod 10rev = rev · 10 + digitx after x ÷ 10
112330 · 10 + 3 = 312
21223 · 10 + 2 = 321
31132 · 10 + 1 = 3210

When x becomes 0 there is nothing left to read and rev is the answer. Every digit problem is a variation on this loop. Adding digits (Add Digits) replaces "rev · 10 + digit" with "sum + digit". Checking a palindrome reverses only half the digits and compares the halves. Plus One walks from the right, adding and carrying. Square root by hand is the same idea with the decimal places found one at a time, though binary search is the usual code.

The one new piece is the overflow guard. If the answer must fit in a 32-bit signed integer, the largest value is 2,147,483,647. Before computing rev · 10 + digit, check that rev is below 214,748,364, or equal to it with the digit at most 7; otherwise the next step would exceed the limit and you must return 0.

Why it is correct

The invariant is that rev holds, in reverse, exactly the digits that have been removed from x. Write the original number as dk … d2 d1. Before any step rev is 0 and nothing has been removed, so the claim holds trivially. Each step removes di, the current last digit, and appends it to rev. Appending a digit on the right of a decimal number is exactly rev · 10 + digit, because the old digits all move one place left. So after the step rev reads the removed digits in the order they were removed, which is right to left. When x is 0 all digits have been removed and rev reads all of them backwards.

Negative numbers need one decision: strip the sign, run the loop, put the sign back. In most languages the remainder of a negative number is negative, which would quietly break the loop.

Why it is fast

Each step removes one decimal digit, and a number x has ⌊log10 x⌋ + 1 digits, so the loop runs that many times: 10 steps for a 10-digit number. That is O(log x) time, with two integer variables of memory. The string approach is also linear in the digit count but costs an allocation and gives you no overflow check for free.

How to recognise it in an interview

Cues: "digits", "reverse", "palindrome number", "sum of digits", "add one to the number represented by", "without converting to a string", and any mention of 32-bit overflow. Say: "I will peel digits with mod 10 and integer division by 10, and check overflow before each multiply".

Reverse Integer is the loop above with the guard. Palindrome Number reverses the number (or just its lower half) and compares; negative numbers are never palindromes. Plus One is the carry version: add 1 to the last digit, and while a digit became 10 set it to 0 and carry into the next one, remembering to grow the array when the carry falls off the front.
