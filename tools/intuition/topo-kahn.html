Start with what you would do by hand

Four courses: 0 has no prerequisite; 1 needs 0; 2 needs 0; 3 needs both 1 and 2. In what order can you take them? By hand you say "0 has nothing before it, so take 0 first. Now 1 and 2 are free, take them. Now 3 is free." You never wrote a rule, but you used one: take something that has nothing left waiting on it.

With 4 courses you can see what is free. With 5,000 courses and 20,000 prerequisites you cannot see it, and if you rescan the whole list every time you take a course that is 5,000 × 20,000 = 100 million checks. We want to keep the "how many prerequisites are still waiting" number for every course and update it cheaply.

Build the structure, one piece at a time

First, store the arrows: for each course, the list of courses that need it. 0: [1, 2], 1: [3], 2: [3], 3: [].

Second, a counter per course called its in-degree: how many arrows point into it, that is, how many prerequisites it still has. Count once at the start:

course0123
in-degree0112

Third, a queue of courses whose in-degree is 0. These can be taken right now. Start: queue = [0].

Now the loop. Take 0 from the queue and write it to the output. For every arrow out of 0, lower the target's counter by one, because one of its prerequisites is now done. 1 drops to 0, so enqueue it; 2 drops to 0, so enqueue it. Queue = [1, 2], output = [0]. Take 1: arrow 1 → 3 lowers 3 to 1, still waiting. Take 2: arrow 2 → 3 lowers 3 to 0, enqueue it. Take 3. Output = [0, 1, 2, 3].

If the prerequisites contain a loop, every course in the loop keeps a counter of at least 1 forever, because each is waiting for another member of the loop. The queue runs dry with courses left over. That is how the same loop also detects cycles: fewer than V courses in the output means a cycle.

Why it is correct

The invariant: a course is in the queue only when its counter is 0, and its counter is 0 only when every prerequisite has already been written to the output. Each decrement happens exactly when a prerequisite is written, so the counter always equals the number of prerequisites not yet output. A course therefore never appears before anything it needs, which is the definition of a valid order.

Why it is fast

Counting in-degrees looks at each arrow once. The loop writes each course once and, when writing it, touches each of its outgoing arrows once. So:

work = V + E

For 5,000 courses and 20,000 prerequisites that is 25,000 steps instead of 100 million rescans.

How to recognise it in an interview

Cues: "order such that every dependency comes first", "build order", "which words come before which" in an unknown alphabet, "can all be done". The first thing to say: "count in-degrees, queue the zeros, and peel." Course Schedule II asks for the order itself; this output list is the answer. Alien Dictionary first turns adjacent words into arrows between letters, then runs exactly this peel. Minimum Height Trees peels leaves (degree 1) layer by layer with the same queue idea.
