Start with what you would do by hand

Six numbers: 1, 3, 5, 7, 9, 11. You need the sum of the first k of them, for various k, while the numbers keep changing. The sum of the first 5 is 1 + 3 + 5 + 7 + 9 = 25. With a table of running totals (1, 4, 9, 16, 25, 36) that is one lookup, but adding 2 to the fourth number forces you to rewrite the last three totals, and with a million numbers that is a million rewrites. Adding up from scratch each time is a million steps per question instead. We want both the question and the change to cost a few steps.

Build the structure, one piece at a time

Piece one: number the positions from 1, not 0, and write each position in binary. The lowest set bit of a position, written lowbit(i), is the value of its rightmost 1: lowbit(6) = 2 because 6 is 110, lowbit(4) = 4 because 4 is 100, lowbit(5) = 1.

Piece two: a second array, tree, where slot i stores the sum of a block ending at i whose length is lowbit(i). So slot 1 covers position 1 alone, slot 2 covers positions 1 to 2, slot 3 covers position 3 alone, slot 4 covers 1 to 4, slot 5 covers 5 alone, slot 6 covers 5 to 6:

Piece three: a prefix sum by walking down. To sum positions 1 to 5, start at i = 5, take tree[5] = 9, then remove the lowest bit: 5 − 1 = 4. Take tree[4] = 16, remove the lowest bit: 4 − 4 = 0, stop. Total 25, from two slots. The blocks visited, 5..5 and 1..4, tile the range 1..5 exactly.

Piece four: a change by walking up. Add 2 to position 4. Every slot whose block contains position 4 must grow by 2. Start at i = 4, add 2 so tree[4] = 18, then add the lowest bit: 4 + 4 = 8, which is past the end, stop. Had the array been longer, slot 8 (covering 1..8) would be next.

Why it is correct

The invariant is that tree[i] equals the sum of positions i − lowbit(i) + 1 through i. The downward walk from i takes the block ending at i, then jumps to i − lowbit(i), which is exactly the position just before that block, and takes the block ending there, and so on until 0. The blocks are adjacent and end at position i, so together they cover 1..i once each.

The upward walk must visit every slot whose block contains position p. A slot j > p contains p exactly when j − lowbit(j) < p, and the next such slot after p itself is p + lowbit(p): adding the lowest set bit clears it and carries, producing the smallest larger number whose block reaches back past p. Repeating the step visits all of them and nothing else.

Why it is fast

Each downward step removes one set bit from i, and i has at most log2 n + 1 bits, so a prefix sum reads at most that many slots. Each upward step moves the lowest set bit at least one place to the left, so an update also takes at most log2 n + 1 steps:

query and update ≤ ⌊log2 n⌋ + 1 slot visits

For a million positions that is 21 steps for either operation, against a million for one of them in the by-hand approaches. The memory is one extra array of n numbers, and the code is two loops of three lines each. A segment tree does the same job with more memory and more code; the Fenwick tree is the compact choice when only prefix sums and point updates are needed. A range sum from l to r is prefix(r) − prefix(l − 1).

How to recognise it in an interview

Cues: "count how many earlier elements are smaller", "prefix sum with updates", "number of inversions", or any scan where you must ask how many already-seen values fall below a threshold. Say: "I will scan once and keep a Fenwick tree over values, so each count and each insert is O(log n)".

Count of Smaller Numbers After Self scans from the right: for each number, query the prefix sum of values below it, then add 1 at its value. Reverse Pairs scans the same way asking how many seen values exceed 2 × the current one. Range Sum Query Mutable is the plain point-update, range-sum use.
