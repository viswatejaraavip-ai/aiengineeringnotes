Start with what you would do by hand

Given 1, 2, 3, −2, 2 and the target k = 3, count how many contiguous stretches of the list add up to 3. By hand you try every start and every end: 1+2 = 3 yes; 3 alone yes; 3 + (−2) + 2 = 3 yes; 1+2+3−2−1 … and so on. The answer is 3 stretches.

There are about n2 ÷ 2 start–end pairs, and adding up each stretch from scratch costs up to n more, so the plain method is O(n3); keeping a running total as the end moves brings it to O(n2). For a list of 100,000 numbers that is still five billion additions.

Build the structure, one piece at a time

Piece one: prefix sums. Let P[j] be the sum of the first j numbers, with P[0] = 0. For our list: P = 0, 1, 3, 6, 4, 6. Now any stretch is a subtraction:

sum of positions i … j − 1 = P[j] − P[i]

Piece two: turn the question around. A stretch ending just before j sums to k exactly when P[i] = P[j] − k for some earlier i. So at each j we need to know: how many earlier prefix sums equal P[j] − k? That is a counting question, and a hash map from prefix value to count answers it in one step.

Walk once, keeping the running prefix and the map. Seed the map with {0: 1}, which stands for the empty prefix before the first element. At each number: update the prefix, look up prefix − k and add its count to the answer, then record the prefix in the map.

The final answer is 4: the stretches 1+2, 3, 3−2+2, and 2+3−2 (positions 1 … 3). The by-hand count missed one, which is exactly why the method is worth having.

Why it is correct

The invariant: when we are at position j, the map holds the count of every prefix P[0] … P[j − 1]. We record each prefix after using it, so this holds. Then the number we add at step j is exactly the number of i < j with P[i] = P[j] − k, which by the subtraction formula is exactly the number of stretches ending at position j − 1 that sum to k. Summing over all j counts every stretch once, grouped by where it ends. Looking up before recording matters: an empty stretch (i = j) sums to 0 and must only count when k = 0, and the seed {0: 1} handles the stretches that start at position 0.

Why it is fast

One pass of n steps, each doing one addition, one lookup and one insert, all about one step: O(n) time, O(n) memory for the map. Five billion additions became a few hundred thousand operations. The gain comes from never re-adding a stretch: the prefix sums store every partial total once, and the map turns "find a matching earlier total" from a scan into a lookup.

How to recognise it in an interview

Cues: "count subarrays whose sum is", "subarray sum divisible by", "equal numbers of 0s and 1s" (map 0 to −1 and look for sum 0), "longest subarray with sum k" (store the first index instead of a count). The first thing to say: "A subarray sum is a difference of two prefix sums, so I will count earlier prefixes equal to current minus k with a hash map."

Subarray Sum Equals K is the example. Subarray Sums Divisible by K keeps prefixes modulo k, because two prefixes with the same remainder differ by a multiple of k. Path Sum III is the same pattern walking down a tree, where the "prefix" is the sum from the root and you remove it from the map when you backtrack.
